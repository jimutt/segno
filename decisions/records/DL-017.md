## Context

The element gets file URLs (or a prebuilt sync map) and an audio file, and must keep the markers in step with the audio. Things go wrong in practice: files that don't belong together, missing note positions, audio exported without repeats.

## Decision

**Loading.** Whenever an input attribute changes, the element starts a new load and cancels the previous one (`AbortController`):

- with `sync` (a URL attribute, or a sync map set on the `sync` property), it uses that map; it needs nothing from the SVGs;
- otherwise it fetches the `positions` file, the optional `notes` file and the text of each SVG page in parallel, reads each page's size (`readViewBox`) and builds the map (`buildSync`, DL-002). A `notes` file that fails to load or fit only drops the note cursor.

URLs resolve against the document. The pages and audio show and play while the map loads. The element remembers which inputs it applied: an element upgraded with its attributes, or moved to another place in the page, loads nothing twice and keeps its position (moving it with `moveBefore()` even keeps it playing). A new audio source stops playback and keeps the tempo.

**Fallbacks.** The player never blocks playback on the markers:

- a map that fails to load or build → pages and audio, no markers, and a console warning;
- audio shorter than the last event's time ("Play repeats" was off) → the same, with a warning that says so;
- a sync map with an unknown version `v`, or entries of the wrong shape, is rejected the same way.

While there are no markers, `sync` is `null` and `playBar()` rejects, so a site can tell.

`canplay` fires once the audio can play and the load has settled, either way.

**The loop.** While playing, a `requestAnimationFrame` loop reads `audio.currentTime` and updates the markers: the bar marker at `t + bar-lead × playbackRate`, the note cursor at `t + note-lead × playbackRate` (DL-006). While paused, the markers update on `seeked` and `timeupdate`. Before playing, the markers show where playback will start. `barchange` fires when playback moves to another bar, or to the same bar's next pass through a repeat (`detail.event` tells them apart); the marker only moves when the bar changes.

**Follow.** With the `follow` attribute, when the playing system leaves the viewport the player scrolls it to about a quarter from the top of the scrolling area (`scrollIntoView` with a `scroll-margin-top` of a quarter of the viewport's height), smoothly unless the user prefers reduced motion.

## Rationale

Markers that are wrong are worse than no markers, so every mismatch falls back to plain playback with an explanation for the developer. Reading `currentTime` each frame keeps the markers in step through seeks, tempo changes and stalls without any timing of their own.

## Consequences

- With file URLs, the SVGs are fetched twice (as text and as images); the HTTP cache makes the second one free. Sites that prebuild maps avoid the text fetch entirely.
