## Context

Segno will ship a core library, a web component and a CLI. They could be one package or several. Users need an install that works in Node (for build-time sync maps), in bundlers, and straight from a CDN.

## Decision

- **One npm package, `segno`**, with subpath exports: `segno/core` (the library) now; `segno/player` (defines `<segno-player>`) and a `segno` CLI bin when they exist. There is no root export, so every import says what it uses.
- **ESM only.** Node 22 or later (`engines`), and evergreen browsers.
- **Built with `tsc`** to `dist/`, with type declarations, declaration maps and source maps; the TypeScript sources are published too (DL-007).
- `sideEffects: false` while the package holds only the core.

## Rationale

- One install and one version to track for users; the core, the player and the CLI change together and are tested together.
- Subpath exports keep the core usable on its own without pulling in the player, which is the reason a separate core package would exist.
- Node 22 is the oldest maintained LTS line when this was decided; ESM-only avoids dual-package hazards and is what browsers and CDNs load.
- Plain `tsc` output keeps the published code readable and maps one to one onto the sources.

## Consequences

- When `segno/player` is added, its module defines a custom element on import, so it must be listed in `sideEffects`.
- The browser bundle for CDN use (a single file) will need a bundler step next to `tsc`; record that choice with the player.
- If a consumer ever needs the core without the package's other dependencies, splitting it out stays possible: the subpath already isolates it.
