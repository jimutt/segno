## Context

Segno is published to npm. Releases should be reproducible from the repository, and their provenance verifiable, without long-lived secrets where avoidable.

## Decision

- **Changesets** for versioning and changelogs: every pull request that changes the published package adds a changeset (`npx changeset`).
- The **Release workflow** (`.github/workflows/release.yml`) runs on every push to `main`, using the separate `changesets/action` steps so each job gets only the permissions it needs:
  - `select-mode` decides whether there are changesets to version or a version to publish;
  - `version` opens or updates a "Version Packages" pull request (contents and pull-requests write);
  - `publish` runs every check, then `changeset publish` (contents write for tags and GitHub releases, `id-token: write` for npm).
- **npm trusted publishing (OIDC)** with provenance: no npm token is stored. The publish job runs in a GitHub environment named `npm`, which the trusted publisher on npm is tied to and which can require approval. `publishConfig` sets `access: public` and `provenance: true`.
- A trusted publisher can only be configured for a package that already exists on npm, so the **first** publish uses an `NPM_TOKEN` repository secret. Remove that secret once the trusted publisher is set up.
- Before 1.0, versions are `0.x`: the core's first release is `0.1.0`, a pre-release in all but name.

This replaces the initial plan of always publishing with a token stored as a repository secret.

## Rationale

Trusted publishing gives each release a short-lived credential bound to this repository, workflow and environment, so there is no token to leak or rotate, and provenance is attached automatically. Splitting the Changesets steps keeps `id-token: write` away from the job that opens pull requests.

## Consequences

- On npm, after the first publish: add a trusted publisher for `jimutt/segno`, workflow `release.yml`, environment `npm`; then delete the `NPM_TOKEN` secret.
- The package is marked `private` while it has nothing to publish, so a push to `main` can't publish an empty package.
- In the repository settings, GitHub Actions must be allowed to create pull requests for the "Version Packages" pull request.
