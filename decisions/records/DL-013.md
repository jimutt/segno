## Context

Segno will have a demo site (DL-001), and changes to the player are easiest to review by trying them. Each pull request should therefore get a preview of the demo at its own address.

GitHub Pages gives a repository one site and has no built-in previews per pull request. Hosting services (Cloudflare Pages, Netlify, Vercel) have them, but they need an account and a secret outside GitHub.

## Decision

The demo is hosted on **GitHub Pages, published from the `gh-pages` branch** ("Deploy from a branch" in the repository's Pages settings). `.github/workflows/pages.yml` writes to that branch:

- on every push to `main`, the demo goes to the root of the site (`https://jimutt.github.io/segno/`), using `JamesIves/github-pages-deploy-action` with `clean-exclude: pr-preview/` and `force: false`, so it neither deletes the previews nor force-pushes over them;
- for each pull request from a branch of this repository, `rossjrw/pr-preview-action` publishes the demo under `pr-preview/pr-<number>/`, comments the link on the pull request, updates it on every push, and removes it when the pull request closes.

The demo lives in `demo/`. `npm run build:demo` (`scripts/build-demo.mjs`) builds it into `site/` and stamps the commit it was built from. Its links and assets are relative, so the same build works at the root and under a preview path.

Pull requests from forks get no preview yet: their token can't push to `gh-pages`, so the preview job is skipped for them.

## Rationale

- Free, no services or secrets beyond GitHub, and previews live next to the demo they preview.
- The preview action handles the comment, updates and cleanup; the main deployment only has to leave its folder alone.
- Stamping the commit makes it obvious which version a preview shows.

## Consequences

- The `gh-pages` branch accumulates a commit per deployment. It holds only built files, so its history can be squashed if it ever grows too large.
- Previews share the demo's origin, and with it the browser's storage for the site; the demo must not rely on storage that a preview could disturb.
- Supporting fork pull requests later needs a two-stage setup: an unprivileged `pull_request` workflow builds the site and uploads it as an artifact, and a `workflow_run` workflow deploys that artifact without running any of the pull request's code. Running the pull request's code with write access (`pull_request_target`) is not an option on a public repository.
